## Assessment and evidence boundaries

The most consequential failures cross a boundary between modules: a UI edit reconstructs and weakens policy; a redactor refresh overwrites a new credential registration; accepted steering is stored but never reconstructed; cancellation ends an outer future while an inner script worker survives; a channel sends an idempotency header that its receiver ignores. Several desktop controls also promise behavior that the daemon or native platform does not implement.

The fixes below preserve existing authority checks and use the owning implementation for persistence, redaction, provider configuration and runtime state. They do not establish complete OS isolation, power-loss atomicity or native desktop correctness. The unfixed findings and the ten highest-priority verification gaps remain part of the result.

Closing review snapshot: **37 confirmed findings (21 high, 15 medium, one low)**. The **17 audit fix/test PRs address 22 findings**; owner-side follow-ups in **#51 and #56 address five more**. **Ten remain open (seven high, three medium)** at the explicitly reviewed heads. The audit PRs add **95 registered test cases (68 UI, 27 Rust)**; #69 also rewrites one existing test. This count includes positive controls and additional invariants, not 95 independently failing baseline reproductions. Three updater cases are Unix-only. The ten verification-gap groups are separate from the confirmed-finding count.

**Evidence vocabulary**

- **Reproduced:** a named test or bounded harness executed the actual affected implementation and observed the failure. Fake providers, clocks, tools and local HTTP servers replace external dependencies; they are not live-service or native-OS proof.
- **Source-confirmed:** a concrete failure follows the traced implementation or an API contract, but the full timing, crash or packaged-native scenario was not executed.
- **Latent:** the failure is confirmed in a public library/API, while a normal shipped-application caller was not found. This qualifies deployment reachability, not the regression result.
- **Unverified candidate:** a plausible failure still lacks sufficient execution or threat-model evidence. These are separated from confirmed findings.

All file:line references use the baseline above unless an exact PR review head is named. Line numbers are historical anchors, not promises about later revisions. Severity is impact-based: **high** for authority/trust loss, uncontrolled effects or serious state loss; **medium** for bounded availability, correctness or contract gaps. No blocker was assigned merely because a risk was unverified.

The explicitly excluded live-view/screencast areas, permission-engine egress gate, host roles, agent-router, provider-catalog, mcp-bridge, cli-provider, plugin-host and builtin browser/desktop tool files were reviewed without edits. Active token-isolation work was reviewed rather than patched. This report is the only file changed by the report branch.

## 1. Agent lifecycle, cancellation and accounting

### A6-CORE-01 — medium — cancellation and graceful pause are ignored while planning

**Source:** crates/task-runtime/src/runtime.rs:340, baseline.

**Evidence:** reproduced. **Fix:** PR #53.

AgentLoop::drive calls Runtime::start/resume, which enters drive_inner and awaits TurnExecutor::next_step. Execution had cancellation selection; planning did not. An indefinitely pending planner could hold cancellation forever. Even a bounded planner could finish after graceful pause and still admit a new side effect or commit success.

Four tests fail on the original implementation: pending-planning cancellation and shutdown tests time out; a pause-during-planning test reaches a prohibited execution sentinel; another observes Succeeded instead of Paused. Selecting cancellation against planning and checking cancellation/pause again before consuming its result fixes both the hang and transition race. The normal router already has a two-second bound, which limits the usual hang but does not remove the race or the public runtime defect. Cancellation cannot undo an effect already committed by an executing future.

### A6-CORE-02 — high — provider usage can overflow budget accounting and strand a run

**Source:** crates/agent-core/src/subagent.rs:487, model_tokens, baseline.

**Evidence:** reproduced with fake provider usage. **Fix:** PR #59.

Provider ChatChunk::Usage becomes persisted ModelOut.usage, then plan_next/descendant accounting sums it before enforcing token guards. Both the per-step prompt-plus-completion addition and iterator sum were unchecked u64 arithmetic. A malformed counter, or a sum of representable counters, panics debug builds and wraps release builds. The panic leaves a durable Running row without a driver; wrapping defeats the budget.

The two full-loop regressions cover a single overflowing usage record and accumulation across model steps. Both fail before, with the run remaining Running. A saturating fold across both fields now matches descendant-total behavior and forces the budget guard to observe exhaustion. The fix validates arithmetic, not the provider's claimed billing accuracy.

### A6-CORE-03 — high — accepted steering is lost on restart or arrives after resumed inference

**Source:** crates/agent-core/src/agent.rs:487 and :1010; shared.rs:837; router.rs:590–591, baseline.

**Evidence:** reproduced through actual loop recovery. **Fix:** PR #63.

send_user_message stores the chat row and enqueues steering in CtxState. Restart reconstruction creates an empty queue. build_messages excludes current-run chat rows and replays durable user steps instead, so accepted rows that never became STEP_USER disappear. Replaying an interrupted model step can also precede a newly restored correction.

The fix persists first, enqueues the stored representation, reconstructs unconsumed user rows from durable user-step intents, and plans pending steering before interrupted inference. Identical messages remain distinct inputs. A durable intent is considered consumed because history already uses its input and retry updates that row.

Two original-source tests show the first resumed request missing both accepted corrections. Additional regressions prevent replay of consumed corrections and verify steering continues a scheduled tool run after approval. The scheduled test checks prior tool output stays explicitly fenced and labeled as untrusted data through the existing workflow helper. Next-turn queues remain memory-only; this fix applies to accepted steering within an existing run.

### A6-CORE-04 — high — steering writes raw secrets into durable step history

**Source:** crates/agent-core/src/agent.rs:487; exec.rs:274; task-runtime persistence, baseline.

**Evidence:** reproduced with a registered sentinel secret. **Fix:** PR #63, same persistence-before-enqueue change.

Steering previously enqueued the raw string while separately writing a redacted chat row. plan_next placed that raw value in STEP_USER.input, and the runtime persisted input/output verbatim. Initial user input follows the redacted storage path, so the two routes disagreed. Outbound provider redaction did not remove the secret from the database or later state export.

pending_steering_redacts_persisted_steps pauses at approval, accepts a fake registered secret, denies the original action and inspects durable steps. It finds the secret before the fix. insert_user_message now returns the exact redacted value it stored, and that value alone enters the steering queue. SharedRedactor's separate registration race is A6-SEC-01.

### A6-CORE-05 — high — discovery executes a replacement tool under stale approval

**Source:** crates/agent-core/src/shared.rs:995–1038; exec.rs:785–939; crates/agent-router/src/surface.rs:257–263; crates/mcp-bridge/src/manager.rs:442–450, baseline.

**Evidence:** deterministic actual-loop regression executed and failed. **Not fixed:** the resolution/dispatch contract belongs to the expressly excluded active agent-router/MCP worker areas.

Shared::resolve_call captures the effective target specification and arguments for use_tool while retaining the generic wrapper as its executable. Permission checking and approval use that captured specification. UseTool::call then performs a fresh registry lookup. A replacement registered under the same name can execute with another effect/category under the old decision; rechecking the existing permit does not reclassify the new executable.

use_tool_cannot_execute_a_replacement_under_a_stale_approval starts a real loop with an Fs Write tool and a hard Shell Deny. While its approval is pending, the fixture unregisters it and registers a Shell Destructive tool with the same name. Approving the old tool executes the replacement once; the expected-zero assertion fails. This is one executed hermetic regression, not a hypothetical timing claim. Production MCP refresh also unregisters/registers named adapters, and server configuration supports category/trust metadata changes. A live MCP reload exploit was not executed.

Direct calls retain the resolved Arc; discovery should likewise pin the executable whose specification was checked, or resolve and authorize the final executable before dispatch. No forbidden production code was edited, and the proof-only failing test is not shipped as a fix.

## 2. Permissions, secrets and scoped authority

### A6-SEC-01 — high — a refresh can forget a newly registered credential

**Source:** crates/agent-core/src/config.rs:165–184; apps/cli/src/serve.rs:162–165, :807–810, :847–855; agent-core/src/shared.rs:928–932, baseline.

**Evidence:** deterministic real-method race. **Fix:** PR #61.

RegisteringStore::set writes a credential and calls SharedRedactor::register. Background polling and run-start refresh rebuild the same shared redactor. replace copied pinned values, released their mutex, then published the replacement. Registration could pin/add a new value in that gap and return successfully, only for the stale replacement to erase its live mask.

The fix retains the pinned-values guard through publication, preserving the lock order. Two test-only scheduling callbacks and channels drive the actual replace/register methods through the lost-update interleave, without sleeps or a probabilistic loop. The original implementation fails contains_secret; the fixed test verifies raw/encoded forms and a later refresh. Impact includes provider/event redaction during the gap, especially values without a generic secret-shaped prefix.

### A6-SEC-02 — medium — invalid sender input leaves an orphan remote inbox

**Source:** apps/cli/src/email_host.rs:533–554 and cleanup :574–581; crates/daemon-api/src/email_routes.rs:74–84, :110–125, baseline.

**Evidence:** reproduced with a local fake AgentMail server. **Fix:** PR #60.

POST /v1/email/accounts validates credentials and bot ownership, then EmailHost::add_agentmail creates the remote inbox. Sender parsing happens afterward inside a struct initializer. Its early error exits before cleanup, leaving an allocated remote inbox without a local account.

The sender list is now normalized and validated before provider creation. The regression uses an invalid address and requires zero provider requests, no saved account, no stored key and no config file. It fails before on the request count. Repeated invalid requests could otherwise consume provider inbox quota.

### A6-SEC-03 — high — the disk CLI token can invoke a more privileged bot

**Reviewed head:** PR #37, 733f40ce8381375f28aa5a874fdd964569fb6b20.

**Source:** crates/daemon-api/src/auth.rs:36–40, :451–464; lib.rs:574, :577–578; routes.rs:471, :521, :529; agent-core/src/agent.rs:499 at that head.

**Evidence:** source-confirmed authority path; no packaged OS exploit. **Not fixed:** active token-isolation design in PR #37. [Posted review](https://github.com/emreocell/Praxi-Bot/pull/37#pullrequestreview-5906708756).

The on-disk token maps to LocalCli without a bot identity. It may list bots, create a chat and send messages for any bot owned by the installation user. The idle message path starts a normal Human turn. A same-user bot child that obtains this credential can ask another bot to use the latter's mailbox/MCP access and grants without forging an approval decision.

This is a residual containment gap in a PR that explicitly acknowledges partial OS sandboxing, not a regression introduced by the token split. A scoped principal or a child boundary that prevents obtaining any owner-message principal needs a two-bot, disjoint-scope regression.

### A6-SEC-04 — medium — Windows replacement durability relies on an unsupported flag

**Source:** crates/secret-store/src/publish.rs:10–13, :48–54, baseline.

**Evidence:** source/API-contract confirmation; no observed power-loss outcome. **Not fixed:** a native publication change needs explicit durability and ACL/attribute compatibility work.

Existing encrypted stores are published with ReplaceFileW and REPLACEFILE_WRITE_THROUGH, while surrounding comments claim write-through durability. [Microsoft's ReplaceFileW documentation](https://learn.microsoft.com/en-us/windows/win32/api/winbase/nf-winbase-replacefilew) identifies that flag as unsupported. The new-file path uses MoveFileExW, a separate API.

The Windows test verifies resulting content and creation-time preservation, not persistence after power loss. Replacing the API casually could change security descriptors, attributes or creation time. The confirmed defect is the unsupported guarantee; no claim is made that every secret write is lost or that a specific NTFS crash outcome was reproduced.

### A6-SEC-05 — high — credential path protection omits actual vault staging and lock files

**Reviewed head:** PR #37, 733f40ce8381375f28aa5a874fdd964569fb6b20.

**Source:** crates/builtin-tools/src/files.rs:941–947; secret-store/src/file.rs:221–225; secret-store/src/transaction.rs:42 at that head.

**Evidence:** source-confirmed filename/boundary mismatch; full publication race not executed. **Not fixed:** belongs to PR #37's active guard. [Posted review](https://github.com/emreocell/Praxi-Bot/pull/37#pullrequestreview-5906757490).

The guard recognizes suffixes such as .tmp and .bak, but the store writes secrets.enc.&lt;pid&gt;.&lt;uuid&gt;.tmp and uses secrets.enc.lock. Those sibling files are outside protected vault/secrets directories and do not match the auxiliary-name guard. Brokered file tools can consequently mutate/remove encrypted staging files or unlink the stable transaction lock.

On Linux, unlinking a held sidecar lets another writer lock a new inode, defeating the store's explicit never-unlink invariant. The impact is credential-file integrity and writer serialization. The temporary payload is ciphertext: this finding does not claim observed plaintext disclosure. Tests should use the real unique-temp and lock formats and preserve exact explicit grants.

## 3. Persistence, migrations and restore

### A6-PER-01 — medium — a valid SQLite file can replace working state with an unusable schema

**Source:** crates/state-bundle/src/install.rs:118–156, baseline.

**Evidence:** reproduced through full export/import. **Fix:** PR #66.

Import checked quick_check, schema version and the message-neutralization query. For a current version, migration is a no-op. A database with DROP TABLE bots or a renamed runs.state column still has valid SQLite pages and archive hashes, yet passed preparation and replaced the destination.

Storage::validate_and_migrate now opens only an existing staged database, checks integrity, migrates, prepares the repository's required column selections and runs foreign_key_check. Import calls this owner-provided validator before any swap. Normal Storage::open is unchanged.

The before regression receives a successful ImportOutcome for the damaged schema. Afterward it requires InvalidDatabase, byte-identical destination DB, unchanged secret, and no backup/staging residue. This checks query shape and declared foreign keys; it does not attest every type, primary key, trigger, index or semantic JSON value in an arbitrarily rebuilt database.

### A6-PER-02 — medium — imported parent cycles reach unbounded runtime recursion

**Source:** same import block; crates/agent-core/src/shared.rs:773–798 and subagent.rs:600–605, baseline.

**Evidence:** invalid-bundle acceptance reproduced; stack overflow deliberately not invoked in the test process. **Fix:** PR #66.

A paused self-parent run satisfies its SQLite foreign key. Import accepted it. Resuming then reaches Shared::ctx, which recursively reconstructs its parent before caching the child; cancellation similarly recurses through descendants without a visited set. Startup recovery alone does not necessarily take this recursive path: resume/cancel is the concrete trigger.

Import now uses a bounded SQLite recursive traversal from root runs. Every row must be reachable within the existing MAX_DEPTH value, re-exported as MAX_SUBAGENT_DEPTH. Tests reject self-parent, mutual cycle, missing parent and a chain one deeper than the limit while preserving destination state; a chain exactly at the limit round-trips. Root depth is zero, and both the initial subagent implementation and main permit depth two.

Runtime defense against separately corrupted live data remains absent. Actual parent links are checked, but imported SubSpec.depth JSON is not reconciled; a forged lower field can permit further later spawns. Those limits are explicit rather than hidden inside a broad schema-attestation claim.

### A6-PER-03 — medium — journal flush acknowledges persistence failure

**Source:** crates/storage/src/journal.rs:117–124, :153–179, :395–415; agent-core/src/shared.rs:910–922, baseline.

**Evidence:** source-confirmed and exercised by the existing failing-sink test. **Not fixed:** requires a separate flush/emit error-propagation and lifecycle contract.

EventJournal::flush returns no error. The writer counts/logs write and sync failures but still acknowledges barriers. Shared::emit treats that acknowledgement as durable-before-broadcast evidence for approval/run-state events. The existing sink_failures_are_counted_and_barrier_still_returns test explicitly encodes this behavior.

A journal error counter exists, but no production daemon/UI consumer was found. The confirmed gap is event durability/replay reporting. This does not establish loss of the corresponding SQLite approval or step row, which is written separately.

### A6-PER-04 — medium, latent — untrusted consolidation overwrites a concurrent user edit

**Source:** crates/memory-store/src/pipeline.rs:158–205; store.rs:276–312; manage.rs:46–56; agent-core/src/memory.rs:181–207 and config.rs:334, baseline.

**Evidence:** deterministic actual-pipeline reproduction. **Fix:** PR #67.

The pipeline reads similar memories, awaits model consolidation, checks the old target trust and updates. A real user edit during that await promotes the current row to User. The stale untrusted update then overwrites the correction and downgrades trust.

The regression first permits an ordinary untrusted update, then has the fake consolidator call the real store.edit at the exact decision boundary. The original implementation replaces “Store opens at eleven” with stale “Store opens at ten.” A private helper now checks required current trust within the mutation transaction, before row/index/journal changes; mismatch becomes Skipped. The public update API retains its prior semantics. The test proves the user text/trust survives and no stale journal record appears.

Only library/test MemoryConfig constructors were found; shipped LoopConfig defaults memory to None. This is a confirmed latent library invariant, not a claimed deployed UI exploit. The fix protects trust promotion, not every conflicting edit that retains Untrusted trust. Memory 26 tests and selected clippy passed; direct-dependent core 181 plus seven CLI integration tests and state-bundle 47 also passed.

## Cross-cutting design inconsistencies

1. **The checked authority must be the executed authority.** UI policy reconstruction, unscoped LocalCli messages, native provider writes to another installation and resumed PC identity each separate a user's choice from the effective authority. Discovery's confirmed checked-specification/executable split in A6-CORE-05 is another instance. Display state and a visible tool name are not stable authority identities.
2. **Serialization and migration must preserve trust metadata.** A6-UI-01, A6-SEC-01, A6-CORE-04, A6-PER-04 and A6-PR46-01 lose restrictions or provenance across different boundaries. Conservative unknown-state behavior must be designed explicitly; a default zero or re-created object can silently mean more authority.
3. **Accepted, durable and attached are separate states.** Steering recovery fixes one gap, but next-turn queues, Telegram admission, scheduler occurrence-to-run attachment and journal failure acknowledgements remain inconsistent. A stable outbound header is insufficient without durable receiver-side enforcement.
4. **Cancellation is an end-to-end contract.** Planning, blocking script workers, active-run discovery and native bridge lifetime all participate. An outer Cancelled status is insufficient if a detached inner future can still commit effects or the Stop UI has no targets.
5. **Duplicated concepts drift.** Runtime queued versus UI pending, generic secret versus provider reference/environment, connected daemon versus local native CLI, and native control state versus daemon run state already disagree. The fixes use existing owner helpers or explicitly unavailable controls rather than inventing parallel contracts.
6. **Schema versions and lifecycle changes require combined integration.** #46 and #54 both introduce version four; #56 overlaps #62's bridge and #58's settings component. Independent green PRs cannot establish a safe combined merge. Exact migration ordering and supported prerelease database histories need review.
7. **A successful API call or unit test proves only its own contract.** A journal barrier can acknowledge failure; a Windows replace flag can be unsupported; a manifest/IPC test cannot prove packaged ACL behavior; a mock header test cannot prove daemon deduplication. Tests should assert the cross-module effect, not only a call or local representation.

## Reproduction and release discipline

Regressions use local fake servers, fake providers/embedders, deterministic channel/notify scheduling, temporary databases/files and isolated worktrees. They do not use real credentials, mailboxes or intentional external effects. Before-fail evidence is recorded separately from after-pass evidence; tests added only after a fix are described as invariant coverage rather than fabricated baseline failures.

For each final PR head, the required gate is workspace formatting, workspace/all-target clippy with warnings denied, changed crates and all reverse dependents (the CI workspace test job includes them), cargo-deny, and applicable UI typecheck/tests/i18n/themes/lint. The Rust workspace matrix runs on Windows and Linux; Node/UI gates, cargo-deny and pinned-Chrome integration run on Ubuntu. No Windows JavaScript or native GUI smoke is implied. API schemas were not changed by the published audit fixes in this ledger.

Relevant reverse dependencies include task-runtime → agent-core/cli/daemon-api/evals/remote-api/state-bundle; agent-core → cli/daemon-api/evals/remote-api/state-bundle; memory-store → those plus agent-core; storage → those plus builtin-tools/desktop/memory-store/node-agent/scheduler/task-runtime/workflow-replay. A library pass alone is therefore insufficient. The first #53 CI failure demonstrates why this gate matters.

Outstanding local environment failures, ignored preexisting live tests, review-only worker findings and verification gaps must remain visible. Merge and release decisions require refreshed exact-head evidence and deliberate resolution of the high residual findings; this audit has not merged any branch.
