# Host leadership limits

Demotion closes automatic admission and stops the scheduler and channels. Runs already admitted (scheduled, webhook, Telegram or chat) continue and can still execute approved tools. This change does not pause or transfer them. Before a planned handover, quiesce those runs; task 057 must implement the durable pause/transfer/resume protocol. Heartbeat demotion has the same in-flight limitation. Permission checks remain in force.

A fresh host that hears a higher active epoch records that leader and epoch and remains fresh, so a later import can still treat it as an empty handover target. The update persists that metadata only. Component startup stays on the normal boot path, and a failed scheduler open cannot replace fresh with a standby checkpoint.

A persisted active owner with paired desktop/host devices waits up to ten seconds for heartbeat metadata before starting components. During verification, automatic admission is closed. Higher epochs demote it and equal active epochs stop both. If peers remain unreachable at the deadline, the persisted owner starts: a partition longer than ten seconds can still cause concurrent owners. There is no automatic takeover or distributed lease. If saving or auditing that startup demotion fails, the daemon logs the error and continues in the demoted state instead of aborting startup.

Peer epochs more than 4096 above the local epoch, or above 1,000,000,000, are ignored. Explicit forced activation can recover legacy or ceiling epochs by saturating at that ceiling. Two active owners at the ceiling still stop on equal-epoch evidence; operator coordination is required.

Ownership, invite, revoke and update actions record the actor and old/new ownership in SQLite before acting. Denied invite and revoke attempts are recorded the same way. Rows describe requested actions, including requests whose later I/O fails; they do not imply successful completion. Pairing tickets and codes are never audited. A phone peer cannot mint any invite. Invites come from the local daemon owner or a desktop peer, which is the desktop "add a phone" flow. A stolen phone therefore cannot pair a second phone that would outlive revocation. Phones can still revoke other phones.

Forced activation uses the last local data. Scheduler startup applies misfire policy; run_once/run_all may repeat effects the other owner already completed. The CLI warns about both missing data and duplicate actions. Non-forced activation of an already active owner does not change the epoch. It does restart a channel whose status is conflict.

The API currently returns no install_command: install-linux.sh is Bash and does not yet implement --join. Create a host invite, install separately and use bot host join until packaging supports an end-to-end command. After three fast Telegram 409 retries the channel reports status conflict and keeps trying getUpdates on an exponential backoff from 30 seconds up to 5 minutes. A successful poll resumes it. GET /v1/channels keeps status conflict until then. Equal-epoch host_conflict messages are judged from the sender's authenticated heartbeat, not from the echoed leader field on the frame.
